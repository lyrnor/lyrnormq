## 行为和持久化边界

新增借用式 append_result_groups，最多四帧、每帧64结果，整组原始正文最多8MiB、
序列化元数据最多32MiB。日志提前验证全部绑定、ID、容量、物理空间及分段数；没有
复制完整索引或整组正文。每帧仍为现有 Results 格式，规则结果及其出站引用在帧内原子。

多个帧可共用一次数据 sync_all，跨段则同步每个脏段。所有必需的同步成功后，才应用
内存状态并回复成功。组不是跨帧事务：写入失败后可能恢复未确认的完整帧前缀。
失败仍 poison owner，重启冷恢复；不会把“未确认可能存在”混成“已确认可以丢失”。
缓存维持可信前缀校验、最后消费者/换代失效，磁盘格式和帧字节不变。

生产阻塞 actor 仅聚合已经排队的连续 Append，最多256结果/8MiB正文/16MiB保守估算，
以64结果拆帧。Heads/Plan/Read/Bind/Begin/Retry/Complete/Close 均是顺序屏障，不跨越
这些命令重排。低负载立即提交，没有等待窗口或聚合定时器。状态操作仍用原同步方式。
纯容量预检 Full 可按原帧顺序回退，保留配额内可接受前缀；checkpoint 自身若 Full，
仍按原规则 poison，随后 fallback 得到 Io 并停止，不能承诺所有 Full 都可继续写。
取消调用者回复不取消必要的落盘，admission 仅在结果确定后释放。

MQTT observer 入队仍是有界 best effort，MQTT ACK 不与出站落盘耦合。本文确认延迟是
基准请求的日志持久化确认，不是 MQTT PUBACK 或 Webhook 完成延迟。

## 测量方法

本地 M4 MacBook Air、16GiB、Rust1.98.1 Release、macOS27.0 内置 FileVault APFS SSD，
数据位于 /private/tmp；环境、余量和负载见 environment.json。非隔离工作站，不能将
这些数字当作生产 Linux/NVMe 容量承诺。所有矩阵顺序运行，性能阶段没有并行测试。

1. 新直接矩阵54次：三类拓扑×1/16/64MiB段×组宽1/4×三轮。每帧最多64结果，
   1KiB正文；单规则单出站和单规则16出站各4096输入；4规则单出站16384输入，
   形成65536结果、约80MiB日志，实际跨越64MiB段，避免大段仅测试空配置差异。
2. 确认矩阵6次：16个生产者、每个最多8个未确认请求、channel容量128，一个日志owner，
   16MiB段、单规则16出站，组宽1/4各三轮。仅领取已排队请求，不人工等待聚合。
   每请求在有界send之前记时，到同步API成功返回记录确认；包含发送背压/排队/应用
   状态，另记录生产者实际观察回复的延迟。这个独立驱动不是生产MQTT路径，且其
   最多128未确认请求限制了实际组宽，不一定填满配置四帧；平均帧/组随数据报告。
3. 原39场景控制矩阵：原topology源码SHA、输入和批量/同步边界保持不变。逐轮核对
   config、pending计数及实际日志字节与phase5h完全一致，不能将新四帧吞吐冒充同边界
   加速。完整原始记录和控制前后统计随附。

所有调用使用生产 sync_all；实际 append data sync 计数来自只读进程内计数器，含
组内轮转，排除初始化、目录、状态操作和checkpoint同步，绝非系统全部fsync计数。
逻辑组调用数不等于同步次数。每轮写入后完整读回所有出站正文并冷重开校验恢复计数。
写入计时包含驱动构造/校验，API组调用计时不含准备；不含后续读回/恢复。

表格各列取三轮中位数；summary.json保留吞吐范围。结果/s是唯一正文结果，乘出站数
才是新建投递引用/s，并非投递成功或MQTT TPS。组调用p99是整组延迟，绝不除以批量
当成单条p99。确认表则使用逐请求时间戳；其通用Samples字段api_call_latency_ns在该
stage表示请求确认样本，engine_seconds仅为样本耗时和，不是并行生产者CPU时间。

RSS为整个基准进程，写完RSS含驱动和索引，峰值还覆盖后续缓存读回、冷重开及清理；
不是纯writer或Broker内存。time原单位bytes、ps为KiB，统一换算MiB。队列预算512MiB、
最多200000投递引用；大分段并不预分配同等大小堆内存。样本为本机短时测试，有负载
与同步延迟波动，尤其16次组调用的p99等于最近秩最大值，不能当作稳定SLA。

### 解读

在16MiB段下，组宽1→4：单规则单出站15,530→55,406结果/s（3.57倍），四规则
13,804→46,700（3.38倍），单规则16出站11,925→38,075（3.19倍）。后者创建约
609,200个投递引用/s，但不是609,200次HTTP成功投递。写完RSS分别约增加0.25、0.33、
0.95MiB；峰值包含后续读回/重开，因此另列，不能把它当作纯写缓冲增加量。

1MiB默认段下组宽4也有提升，但16出站案例跨段将64帧变为25次data sync，而16MiB
只需16次；同一组跨段不能只同步最后一个段。大规则数据实际文件数为86/5/2，表明
64MiB实验确实跨段而非仅配置不同。64MiB没有稳定全面胜过16MiB，尤其短数据全部
落在一段时，差异可能主要是负载波动，不据此声称某个更大值必然更好。

逐请求确认驱动从13,332→18,012结果/s（约35%），平均实际帧/组仅1.80；其最多128
未确认请求和无等待聚合限制了填满四帧。确认p99从12.24→13.64ms，观察回复p99从
12.27→13.92ms，没有延迟改善。Group Commit提高吞吐不保证每条请求更快确认；
不得用直接组调用吞吐或p99替代这组真实请求样本。

原39控制全部保持单帧边界，没有将组宽4偷偷用于对照。历史逐条同步写入部分下降、
读取也有工作站短窗口波动，全部数据原样列出；它们不是此次组提交收益。针对单条
写入下降另外交替旧/新二进制三轮，结果随paired-control记录，既不覆盖控制矩阵，
也不声称消除了系统同步延迟。单个调用每条都等待落盘时，不会获得组提交吞吐。


### 单条控制下降的配对诊断

旧/新二进制交替三轮，共6次，输入2048、1KiB、单规则单出站、batch1，与该控制
场景完全一致。旧版中位数257.5结果/s，新版256.8结果/s，比例0.997；
旧调用p99中位数6.13ms，新版5.99ms。未观察到稳定的代码回退，亦无单条同步
加速；这与同步时延/工作站负载波动解释一致，不证明历史所有差异均由负载引起。
命令、SHA、每轮原始JSON/time及范围保留在paired-control/，不替换39控制。
paired-control.py需要预先保存的旧topology二进制，可从e34b6f8独立worktree构建。

## 配置决定及剩余工作

Group Commit 已默认接入生产actor。保留原1MiB分段默认值，以兼容显式小容量队列和
现有QueueOptions验证；高吞吐部署可用现有参数选择本轮测试的16MiB分段：

```sh
./target/release/lyrnormq --egress-queue-segment-bytes 16777216
```

其他原有启动参数照常添加。配置仍要求queue-max-bytes至少为segment-bytes的四倍，
默认256MiB预算可直接使用16MiB段。64MiB没有稳定全面优于16MiB，单纯加大不是必然
更快；目前不自动改写现有配置或持久化日志。未部署、未重启用户服务、未合并main。

后续：目标Linux/NVMe长时测量、真实生产actor混合Append/Read/状态屏障的聚合程度、
持续排空/背压与确认p99。Begin/Retry/Complete的跨帧Group Commit不在本阶段实现；
没有将其TODO标为完成，也不靠弱化同步推进吞吐。
