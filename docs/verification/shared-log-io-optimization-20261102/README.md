# 共享日志 IO 优化及同场景复测（2026-11-02）

契约：[phase5h](../../contracts/phase5h-journal-io-optimization.md)。先冻结同步和
缓存边界，再由真实日志/质量 Agent 在独立 worktree 实现和独立验证，主控集成。
代码提交 `9049def`、`0cf7609`，质量测试/安全矩阵工具 `c7c4faf`。
生产公共 API、v1/v2 磁盘格式、原子扇出、状态及恢复语义保持不变。

## 诊断与实现

旧二进制先采样实际工作负载，每 1 ms 采样 3 秒，原始 profile 随附：

- 写入阶段 2231 个主线程样本，文件 sync_all 1575、目录同步 119，合计约 76%。
  这是包含阻塞 IO 的主线程驻留采样，不能解释为这些操作使用了 76% CPU。
- 读取阶段 2199 个样本，反复 open 约 1422，约 65%；还有重复 lstat/fstat、定位及 CRC。
  profile 仅用于诊断，不用这些附加工作负载的吞吐替代原矩阵基线。

实施以下优化，不改变每个成功调用必须同步落盘的条件：

1. 帧写入经最多 64 KiB 临时缓冲合并系统调用，显式 flush，随后仍 sync_all，再应用状态。
   CRC 改用安全的 slicing-by-eight，实现与原 CRC/磁盘字节兼容，无 unsafe 或新增依赖。
2. Unix 复用最多 16 个文件描述符，一次读取调用内按段检查身份、权限、硬链接、长度及
   mtime/ctime 指纹，使用定位读取减少逐条打开和 seek。
3. 多消费者结果保留最多 8 MiB 正文、8192 条记录的校验后缓存，跨出站复用正文读取。
   公开返回类型仍为 Vec，返回和 Webhook 封装仍有复制。缓存索引也有固定条数上限，
   8 MiB 指正文上限，不是含元数据的整个进程内存上限。单消费者不额外缓存正文。
4. 合法追加和 Begin/Retry/Complete 前先验证缓存文件，成功 flush+sync 后按段推进可信
   前缀，正常路径不扫描所有缓存条目。文件变化、最后消费者完成及换代正确失效；
   描述符被逐出后重新打开也不能直接信任旧正文。重启从冷缓存恢复。

非 Unix 保留原校验读取路径。缓存依赖独占日志 owner，不是对并发特权文件篡改的防护。
超过缓存工作集或调度局部性差会淘汰，不能承诺任意积压、任意时间跨度只读取一次。

## 验证

- 新计数回归先在旧实现失败：四次跨出站请求读盘四次，优化后一次。交错合法追加、
  Begin、Retry、部分完成仍保持一次读取；最后消费者和换代/重启按预期失效。
- 699 项 Workspace Rust 测试通过，其中日志 52 项。独立基准及公共 API 完整性测试
  共 18 项通过，Workspace/基准 fmt、严格 Clippy 及两个 Release 构建通过。
- 独立测试覆盖缓存后同长损坏、恢复 mtime 后损坏、截断、chmod、硬/符号链接、inode
  替换、FD 逐出后损坏再追加、检查点/重启、重试/部分完成、空正文及超缓存压力。
  CRC 对照标准向量和独立逐位实现；已有失败注入保留 poison/cold-recovery 行为。
- Release MQTT/Webhook 黑盒 62 项通过：共享流 13、耐久队列 12、保序 9、并发 10、
  规则/Webhook 18；包含 SIGKILL、部分完成、稳定 ID、v1 迁移及独立重试。
- 最初 Workspace 运行因沙箱禁止绑定本机测试端口而失败 13 项，保留在

## 测量方法

同一台 M4/16 GiB、相同 Rust 1.98.1 Release、内置 FileVault APFS SSD 的 /private/tmp，
相同单写入者、1 MiB 段、512 MiB 预算。机器不是隔离服务器：原基线起始 load average
约 4.9/6.5/6.1，本轮约 5.9/8.2/7.6。原基线和原始文件保留不覆盖。

使用源码 SHA256 完全相同的 topology 工作负载，配置和顺序保持原样，39 次运行：
1 KiB/128 字节、规则 1/4/16、出站 1/4/16、64 条组提交及逐条同步，每配置三轮。
全部校验消费者正文和计数、采集 RSS；比较脚本逐轮断言原/新 config、统计和实际日志
字节数完全一致。表格逐列取三轮中位数，comparison.json 保留范围及调用 p99。

写入单位为唯一规则结果/s，乘出站数才是新增投递引用/s，不是发送完成速率；除规则数
是合成源输入等价速率。读取单位为消费者投递/s，完整核对所有出站，包含头索引遍历、
CRC 和驱动校验。读取是追加后的 OS 热缓存，不是冷盘带宽；本轮不包含 SQL、HTTP、
Broker 路由、稳态排空和确认写入。缓存交错正确性另由计数和完整性测试验证。

峰值 RSS 为整个基准进程、含缓存及驱动开销，macOS time 原始单位为 bytes；阶段 ps
原始单位为 KiB，均换算 MiB。它不是 Broker 内存或 OS 文件缓存大小。
优化后的读取阶段更短，部分只有几到十几毫秒，对工作站调度敏感；各轮范围必须结合
原始数据看，不将倍数当作生产承诺。没有修改 batch/sync 边界或取最优一轮作为结论。

### 结果解读

1 KiB 的 64 条组提交写入提升 11%–26%，读取提升 10.4–21.8 倍。单规则 16 出站
从约 5.7 万到 124.3 万读取投递/s，峰值 RSS 从 23.95 到 28.78 MiB；额外缓存约
4.8 MiB 进程 RSS。单出站不缓存正文，其峰值 RSS 基本保持原水平。

逐条同步写入未得到稳定提升，单规则 4 出站历史对比下降约 12%；128 字节场景的
写入为原来的 0.86–1.01 倍，不能标为写入全面提升。读取这些场景仍提升 2.3–24.4 倍。
写入受同步等待限制，本轮没有放宽落盘边界；历史前后对比也受机器负载变化影响。
另附交替旧/新二进制配对诊断，保留这些下降，不用诊断数据替换原矩阵。



### 写入下降场景的配对诊断

为调查历史对比中的下降，额外对三个场景交替运行保存的旧/新二进制，各三轮，
偶数轮颠倒顺序，共 18 次，参数和 sync 边界不变。它们不是新增配置，也不替换
前面的 39 次矩阵。原始文件、顺序、SHA256 和范围见 paired/。

|场景|旧版写入结果/s|新版写入结果/s|新版/旧版|
|---|---:|---:|---:|
|128 B，1规则16出站，batch64|10,797|11,484|1.06×|

配对结果下，小包写入提升约 6%，逐条同步基本持平，1 KiB 组提交提升约 24%。
这与同步等待、工作站负载波动的解释一致，但不证明历史差异全部由负载引起；
不能据此声称逐条同步写入已显著优化。需要在隔离 Linux 服务器继续测量。

运行 paired.py 前需有保存的旧二进制 /private/tmp/rmqtt-topology-before-io；
可从 e83904c 在独立 worktree 编译生成，对照其 SHA256。输出 paired 目录同样必须不存在。
