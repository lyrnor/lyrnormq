# 共享规则结果日志性能实测（2026-11-02）

生产引擎基线 `55e99ea`，只新增直接调用生产 Journal 的 `topology` 基准，没有更改
生产实现、同步语义或 Broker 配置。本报告针对 phase5g 共享正文/独立消费者模型，
不能与 phase5f 逐投递正文模型混用。完整命令、二进制/源码 SHA256、原始 JSON 和
`time -l` 输出随附。三个套件共 39 次运行，全部成功。

## 环境与口径

Apple M4 / MacBook Air、10 核（4P+6E）、16 GiB、macOS 27.0、Rust 1.98.1，
Release，单同步写入者。数据目录为内置 FileVault APFS SSD 的 `/private/tmp`，
不是代码所在的外置盘；测试时空闲约 14 GiB。非隔离工作站，同时有其他任务，起始
load average 约 4.9/6.5/6.1，因此本报告是本机实测，不是服务器容量承诺。

- 每条输入匹配所有配置规则；每个 `(规则, 输入)` 生成不同正文，每个结果绑定全部出站。
  不执行 SQL、不发送 HTTP、不包含 MQTT 路由。每个追加批次使用独立 Client，读取覆盖
  所有规则、所有出站和全部结果，无只读队头却将整个积压计入吞吐的情况。
- grouped/small 每轮 4,096 条输入；single 每轮 2,048 条输入。规则数为 1/4/16，
  单规则出站数为 1/4/16。single 测试 1×1、4×1、1×4。
- 每种配置独立进程重复三次，顺序执行，表格各列取中位数，不同列可能来自不同一轮。
  `summary.json` 包含写入吞吐及峰值 RSS 的最小/最大范围。
- “写入结果/s”是独立正文数；“新增投递引用/s”是结果数乘出站数，**不是完成投递数**。
  原始输入等价速率为写入结果速率除以规则数，也不是 Broker TPS。
- append 保持生产 `sync_all`，包含轮转；64 条组提交和逐条同步是不同持久化边界。
  计时包含驱动构造/校验，API 调用延迟另行记录。没有关闭同步来提高数字。
- 读取为追加后 OS 热缓存读取，包含实际文件打开、元数据检查、定位、读取、CRC 和分配；
  wall 吞吐还包含队头索引遍历及正文/规则/Client 校验。不是冷盘顺序带宽。
- RSS 为基准进程内存，包含 Journal 索引、分配器和基准开销，不是整个 Broker 内存。
  写完 RSS 由 ps 采样；峰值由 macOS time -l 采集（原始单位 bytes），覆盖进程全生命周期。
  不等于 OS 文件缓存或纯索引分配量。所有数据量用 MiB，不用十进制 MB。
- 每轮 1 MiB 分段、512 MiB 队列预算，最大 200,000 引用。仅构造有界批次；
  使用独占临时子目录，结束自动清理，不接触现有队列。本轮不测确认/重试状态写入、
  队列排空、稳态压缩、冷读、进程恢复或物理断电。

## 解释与后续

相同 65,536 个投递引用，16 规则×1 出站保存 65,536 份不同结果，单规则×16 出站
只保存 4,096 份结果。1 KiB 正文时，后者实际日志 12.34 MiB，前者 79.53 MiB，
约减少 84.5%；峰值 RSS 23.95 对 52.12 MiB，约减少 54.0%。这是配置及正文数差异
下的实测，不是相同业务输出的新旧代码加速比。增加出站仍会增加引用及索引成本，
不能理解为零空间、零 CPU 开销。

逐条同步仅约 272–287 结果/s，写入调用 p99 的三轮中位数为 6.01–7.43 ms。
64 结果组提交显著摊薄同步成本，但不能将批次 p99 除以 64 当作单消息 p99。
两种模式均是单写入者直接 API 测量；本报告不推断当前运行时会自动达到 64 条组提交。

当前读取实现每个消费者通过 `storage::read_payload` 单独打开文件、检查元数据、
seek/read 并校验正文；多出站共享磁盘正文，但没有共用一次读取/解码。
这条重复工作路径可作为后续 profiling/优化对象，本轮没有采样 profiler，也不将其
直接定性为全部耗时来源。需要补充目标 Linux、NVMe、持续排空和状态写入的长时基线，
才能据此估算生产容量。旧报告中的更高数字不能套用到这些新配置。
