# 集群背压诊断与修复 — 2026-11-03

根因已通过 Linux 同负载诊断确认：JournalOperations 首次拒绝先出现，随后
QuorumPeer/QuorumInsufficient，再发生后台重新接管、缓存失效和会话断连。
Journal-only 修复解除第一层立即拒绝后，上层 DurableOperations 成为下一拒绝点。
两层都改为有界异步背压后，三组均无失败连接，实际发送消息全到达，最终确认完整。
**但 100/s 容量门槛仍未通过，不能把已发送子集无缺失算作全部计划成功。**

## 这里的 Journal 是什么

它是 mqtt-cluster/src/replica.rs 的业务存储类型，不是 Linux journalctl。
每个数据节点使用独立 data.sqlite，SQLite WAL/FULL，单个 Mutex<Connection>。
32 个名额限制已提交阻塞任务；等待该连接锁和事务提交也占名额，不是32条连接
或32次/秒，也不表示实际能并行执行32个SQLite事务。

之前万级追加读写基准来自 mqtt-egress-log：顺序追加、批量Group Commit、缓存与
共享正文读取。当前集群数据Journal没有复用这一实现；会话快照/outbox/收据复制
使用另一套完整记录JSON编码和SQLite事务路径。之前单节点MQTT吞吐也不等于当前
RF3/W2同步状态复制工作量，但复制本身不能作为几个数量级退化的合理解释。

## 修改

- Journal仍32个阻塞任务，增加最多32个异步等待者、750ms等待上限。
- Durable仍32个业务操作、actor队列8、正文总预算16MiB，增加32个有界业务等待者。
- 先计费正文，再预留actor位置，再取全局许可；取消/超时不会提交新Job。
- Work/Forget保持非阻塞跳过；后台跳过与真正拒绝分开记录。
- 不改变W2、状态/收据/outbox原子性、未知写入失效规则、修复代际或持久化schema。

等待数量有限但增加最坏内存预算，尤其Journal等待者保留已解码请求；不能声称峰值
RSS不变。750ms队列超时或满队列仍拒绝，持续超载不保证能够维持任意目标速率。

60连接均匀20/20/20，128B，MQTT5，窗口1，setup并发1，3s预热、30s发送、30s排空。
每组计划3000条，使用相同Rust压测工具，无连接重试或降级QoS。

重复、无效正文及已发送未送达均为0；QoS1 PUBACK、QoS2最终PUBCOMP均等于发送数。
原始样本独立重算数量、最终ACK和p99，见summary.json、after/下报告与gzip样本。
读写IO采样为整个180s窗口，含建连/预热/空闲；不是每个阶段精准归因：vda平均
约1038writes/s、448flushes/s，平均w_await0.734ms、util36.8%，最高util82.6%。
这些数据不足以宣布磁盘硬件已满，不能直接把剩余吞吐问题归咎于云盘。

当前数据面仍有单连接事务串行化、每次完整记录编码、sum(length(data))全表配额
检查、每次SQLite提交的持久化边界、三副本请求放大、后台100ms轮询及一轮等待所有
任务完成等开销。各项耗时比例尚未分段profiling。下一步是测量持久化/锁等待/序列化/
调度占比，评估Group Commit、增量记录和待发送索引/通知驱动；不能靠扩大配额代替。
