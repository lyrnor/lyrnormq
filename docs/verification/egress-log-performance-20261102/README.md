# 分段追加日志性能实测（2026-11-02）

生产日志引擎未修改。代码基线 `7365462`，基准工具集成 `f4c4e46`；原始结果记录
Release 二进制 SHA256。Apple M4（10 核）、16 GiB、macOS27.0、Rust1.98.1。
内置盘为 FileVault APFS SSD，代码盘为 USB 外置 SSD、大小写敏感 APFS、未加密。
这是普通工作站实测，不是服务器或隔离实验室结果；系统负载约4，已有约6GiB
系统 swap 使用，但所有测试进程的 swaps 计数均为0。不可从这两卷直接推断
USB/内置、加密/不加密的单因素性能差异。

## 测量口径

- 串行运行，无并行基准互相争用；每组3次独立进程，正式50个用例总计约199秒。
- 每个 IO 用例1024次追加事务；每次1/8/64条，因此分别1024/8192/65536条。
  128B、1024B是日志原始记录正文大小，不含日志元数据，也不是完整 MQTT 报文。
- 每个追加批次对应一个独立 Client，共1024个 Client；同组记录属同一 Client。
  整体 pending 条数/工作集随批量变化，不是固定数据集的纯单变量测试。
- 真正调用生产 `append_batch`，每事务都 `sync_all`，没有关闭耐久同步。
  API 延迟包含 CRC、编码、索引、轮转和刷盘；吞吐还包含驱动构造/验证开销。
- 读取在追加后进行，不清系统缓存；是热缓存场景。读取计时包含生产打开文件、
  元数据检查、分配、seek/read、CRC；驱动额外逐条比对内容计入吞吐墙钟。
  默认遍历所有Client首批，验证全部记录，无耐久删除混入读取计时。
- **吞吐单位为记录/秒；p50/p95/p99为一次 API 调用（每批）的毫秒数。**
  各次使用nearest-rank，表中是3次独立吞吐和分位数的中位数，不是合并样本p99；
  最大延迟取全部运行中的最大值。不得把批次p99除以条数当作消息p99。
- 单所有者同步引擎，不包含异步actor、规则引擎、MQTT、网络或Webhook时间。
  日志提交批次不等于HTTP批量条数。512MiB容量、20万记录上限、1MiB分段，IO测试
  未达到自动回收阈值。同步语义按当前sync_all实现，未模拟物理断电。
- RSS是整个测试进程峰值，**不包含操作系统文件页缓存**；CPU列也是整进程口径。

## 完整存储循环

128B记录，每批依次执行追加、读取、Begin、Complete；共3次耐久提交，没有HTTP。
每组256个完整循环、3次重复，结果为墙钟记录/秒中位数。实际actor可跨客户端合并
状态提交，本项是同步直接调用模型，不等价于最终Broker投递能力。

## 复现与证据

```sh
CARGO_TARGET_DIR="$PWD/target" cargo build --release --offline --manifest-path benches/egress-log/Cargo.toml
python3 docs/verification/egress-log-performance-20261102/run.py \
  --binary "$PWD/target/release/egress-log-bench" \
  --external-base "$PWD/target" \
  --output /private/tmp/rmqtt-journal-results
```

资源包装脚本使用macOS `/usr/bin/time -l`/diskutil，会动态采集重跑机器信息；
Rust基准可单独运行。汇总脚本默认读取同目录results.json；复制到结果目录后运行。
`run.py`的主体测试逻辑与本次一致，硬件信息采集已从本次已核对的值改为动态读取。

3项基准测试、Fmt、严格Clippy、Release编译及真实小数据冒烟通过。50个正式进程
全部成功，所有读取覆盖/内容检查、循环排空、恢复记录数、Release标志均验证通过；
所有测试队列由工具和私有临时父目录清理。没有打开生产队列，也未执行缓存清理。
原始JSON/time在raw/，聚合数据为results.json，机器信息为environment.json。
只新增基准和验收文档，没有改动生产引擎；下一步应在目标Linux服务器相同负载
复测，再决定句柄缓存、读批处理或刷盘策略优化，不能将本机数字外推到服务器。
